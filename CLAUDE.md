# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

A personal, single-user web app: career profile storage (roles, experience,
certifications), job-opportunity aggregation from a handful of job-board
APIs, and market/advancement insights derived from what that aggregation
collects. Generated from `jay-withers/template-repo-terraform-root`, and
still carries that template's baseline (dev container, pre-commit hooks, CI
workflows, Renovate) — this file covers the application built on top of it.

Deployed as a tenant of the shared Container Apps environment
(`jay-withers/azure-container-apps`), same shape as `jay-withers/gym-log`
and `jay-withers/finances`: its own resource group, Key Vault, storage
account and identity, reaching the shared environment by name via a data
source rather than that repository's Terraform state.

## Public repo, private data

`jay-withers/github-repos`' `repo_defaults.visibility = "public"` applies
unconditionally — this repo is public, same as every other repo in the
account. That has two consequences that matter more here than in most:

- **The profile document is never committed.** It lives only in blob
  storage (or a gitignored local file), never in git.
- **The deployed app needs its own auth even though the repo being public
  says nothing about the app being reachable only by its owner.** Ingress is
  internet-facing (see `terraform/main.container-apps.tf`), so
  `src/career/api/deps.py` gates every page behind a shared passcode — the
  same trade `gym-log` makes, and for the same reason: Container Apps'
  built-in Entra auth needs the `azapi` provider, which no repo in this
  estate uses.

## App architecture

Python/FastAPI, server-rendered Jinja2 (no SPA, no build step) — a personal
tool with occasional data entry and a job review queue doesn't need one.
One package, one image, five CLI subcommands (`career serve|pipeline|
digest|show|seed`, see `src/career/cli.py`); Terraform sets no `command` on
the container app or either job, only `args`, so the Dockerfile's
`ENTRYPOINT` is the single source of truth for the executable's name (see
that file's comment for the outage in `jay-withers/market-agent` that this
guards against).

**Two documents, not one, and not a database.** `src/career/model.py`
defines `Profile` (roles, certifications, skills) and `JobsDocument`
(cached listings, market insights, advancement guidance), each a frozen
dataclass with hand-written `to_json`/`from_json` — not pydantic, not
SQLite, not Postgres. `src/career/store.py` reads each one whole and writes
it back whole, with an ETag precondition for concurrency (adapted from
`jay-withers/gym-log`'s `store.py`) and a local-file fallback when no blob
container is configured, which is what makes `make run` and the test suite
work with no Azure involved. Two documents rather than one because they
change on different triggers and at different trust levels: `Profile` is
edited by hand through the UI and irreplaceable if lost (its storage account
carries `prevent_destroy`, see `terraform/main.storage.tf`); `JobsDocument`
is entirely regenerated by the daily pipeline and can be thrown away and
rebuilt with no lasting loss.

A relational database (SQLite-on-a-volume, or Postgres) was considered and
rejected for the same reason `gym-log`'s training log is a blob rather than
a table: at this scale (a handful of roles/certs, a few hundred cached
listings) there's no query a document store answers worse than "read it,
look at it in Python", and Postgres bills whether or not anything uses it —
`jay-withers/market-agent`'s Flexible Server is the one thing in the estate
that does, at ~£13/month, and it was *forced* there rather than chosen. See
`terraform/main.storage.tf`'s comment for the fuller reasoning.

**`settings.py`/`telemetry.py` are the fourth copy** of a pattern shared
with `jay-withers/repo-agent`, `jay-withers/market-agent` and
`jay-withers/gym-log` (secret resolution: env → `.env` → Key Vault;
Application Insights configured once at start-up). `gym-log`'s own copy
already recorded the tripwire — "copy once more, extract a library the next
time it's tripped again" — and this is that "once more". Re-copy rather than
diverge if a bug needs fixing here; if a *fifth* consumer appears, or a bug
in this file needs fixing a second time, that's the point to actually
extract a shared library.

**Job sources (`src/career/sources/`)**: Reed (keyed, the main UK source,
queried from the profile's job preferences so location/distance/salary are
filtered server-side, and degrading to contributing nothing without its
key) is currently the only source. Arbeitnow (mostly German/Swiss) and
RemoteOK (mostly US-remote) were dropped because neither API can filter by
location, so nearly everything they returned was excluded anyway; Adzuna
was dropped as redundant once Reed covered the UK with server-side
filtering.
LinkedIn has no public job-search API, and scraping it with a personal login
breaks its terms and risks the account. Greenhouse/Lever/Ashby per-company
boards were deliberately deferred — they need a maintained seed list of
companies to watch rather than a broad search, which is more scope than a
v1 needs. Add another source by adding a module with a `fetch(client,
preferences) -> list[JobListing]` function and one entry in
`sources/__init__.py`'s `REGISTRY`.

**Matching vs. advancement guidance is a deliberate deterministic/LLM
split**, the same shape `market-agent` already uses in this account:
`matching.py`/`insights.py` are plain rule-based functions because they run
over every fetched listing and a wrong or slow answer only costs a worse
sort order; `advancement.py` is the one LLM call in the app (DeepSeek, same as gym-log's weekly insight),
because synthesizing "given this profile and this market, what's missing
and what's next" is a reasoning task over a handful of aggregated numbers,
run once a day, where a token-overlap rule has nothing useful to say.

## Terraform layout

`terraform/` is a plain root configuration (not a reusable module — the
`examples/`/`tests/*.tftest.hcl` scaffold the template ships was removed),
following the same file-layout convention every jay-withers Terraform repo
uses: `locals`/`variable`/`output`/`data` blocks live in a matching
`locals*.tf`/`variables*.tf`/`outputs.tf`/`data.tf`, `terraform{}`/
`provider{}` in `versions.tf`, enforced by the local pre-commit hook
`scripts/check-tf-standards.sh`.

Only `dev` is deployed (`terraform/environments/dev.tfvars`) — `data.tf`
resolves the shared platform environment by name, so a plan against an
environment the platform hasn't been applied to fails at plan time, the
same reason `gym-log` plans `dev` alone rather than a dev/stg/prd matrix.

State is remote, in the shared Terraform state storage account managed by
`jay-withers/github-repos` (`terraform/backends/dev.hcl` — partial backend
config, `terraform init -backend-config=backends/dev.hcl`). This repo's
entry in that account's `state_consumers` is what gives it a federated
identity for `ci-terraform`'s credential-free plan job; `AZURE_CLIENT_ID`/
`AZURE_TENANT_ID`/`AZURE_SUBSCRIPTION_ID` (repository variables, not
secrets — OIDC) come from `github-repos`' own
`terraform output state_github_secrets`.

Resources: `azurerm_resource_group`, `azurerm_user_assigned_identity` (the
app's *runtime* identity — distinct from the Terraform-state identity in
`github-repos`), `azurerm_key_vault` (secrets only, no
`azurerm_key_vault_secret` — see `terraform/README.md`'s Secrets section for
the `az keyvault secret set` calls), `azurerm_storage_account` (two
containers, `profile` and `jobs`), `azurerm_container_app` (the web app,
`min_replicas = 0`/`max_replicas = 1`) and `azurerm_container_app_job` (the
daily pipeline, cron `0 6 * * *`, same shape as `repo-agent`'s scheduled
scan and `gym-log`'s weekly insight/daily Garmin-sync jobs), plus a second
job for the weekly digest email (cron `0 19 * * 5`, Fridays — see
`src/career/digest.py`; sent through Resend from `career.jaywithers.uk`,
whose DNS records live by hand in Cloudflare like the app's own).

## Commands

`make` with no target prints the self-documenting help (the default goal).

```bash
make install           # install pre-commit hooks and Python dependencies
make test               # run the test suite
make lint               # run all pre-commit hooks against every file
make run                 # serve locally on :8000 against local files
make pipeline-local       # run the fetch/match/insights pipeline locally
make digest-preview       # render the weekly email locally, without sending
make show                 # print the deployed profile and job cache as JSON
make build/push/deploy   # build, push and roll out the container image
make init/fmt/validate/plan/apply  # terraform/ — see terraform/README.md
```

## Commit messages

Commits must follow [Conventional Commits](https://www.conventionalcommits.org/) — enforced by commitlint at commit-msg time. Examples: `feat: add insights page`, `fix: correct job-listing date parsing`, `chore: bump dependency`.

## Pre-commit config

The language-agnostic baseline (`pre-commit/pre-commit-hooks`, `gitleaks`,
`actionlint`, `shellcheck`, `commitlint`) plus this account's Terraform
additions (`terraform_fmt`/`terraform_validate`/`terraform_docs`,
`scripts/check-tf-standards.sh`, `scripts/tflint-per-env.sh`/
`scripts/checkov-per-env.sh` — the per-environment variants, since the
template this repo was generated from is built for a multi-environment
module even though this repo deploys only `dev`) are inherited from
`template-repo-terraform-root`, documented in that template's own
`CLAUDE.md`. On top of that, this repo adds the Python/container baseline
`jay-withers/gym-log` established: `hadolint` (via `scripts/hadolint.sh`,
resolving `DOCKER_HOST` first rather than the upstream `hadolint-docker`
hook, which fails whenever it's unset) and `ruff-check`/`ruff-format` (rule
selection lives in `pyproject.toml`).

## CI

Workflows are prefixed `ci-` (pull-request checks) or `cd-` (post-merge
delivery):

- **ci-pre-commit**: runs all linters via the shared `pre-commit.yml`
  reusable workflow, `terraform: true`.
- **ci-terraform**: credential-free `terraform init`/`validate` via the
  shared `terraform.yml` reusable workflow. No plan job — this repo
  resolves the shared Container Apps environment through a data source, so
  a plan needs real Azure credentials against an already-applied platform;
  run `make plan` locally instead.
- **ci-python**: the test suite via the shared `python.yml` reusable
  workflow, `extras: dev`, coverage reported (not gated) on `career`.
- **ci-container-build**: builds the image (no push) via the shared
  `docker.yml` reusable workflow, path-filtered to `src/**`/`Dockerfile`/
  `pyproject.toml`/`uv.lock` — deliberately **not** a required status check,
  since a path-filtered job that never runs on some PRs would leave those
  pending forever if required.
- **cd-tag**: auto-tags on merge to `main` (default bump: patch), then
  `cd-publish` (via `./cd-publish.yml`) pushes the image to GHCR — but only
  when the tag/release actually touched `src/`, `Dockerfile`,
  `pyproject.toml` or `uv.lock` since the previous release, so a
  Terraform-only or docs-only merge doesn't publish a redundant image.
